# SkillScope 原始研究设计（规划，不代表当前实现）

SkillScope 准备解决一个问题：给 Agent 增加了技能之后，它为什么反而做得更差？项目希望自动定位有问题的技能组合，并控制相关技能在合适的任务阶段生效。

项目处于设计阶段，以下功能和技术栈均为拟实现方案。

## 解决了什么问题

Skill 可以理解为给 Agent 的一份工作指南，例如如何调试、如何写测试、如何检查代码。

假设有两份指南：一份要求先全面调查原因，另一份要求快速修改并运行验证。它们各自可能有用，但一起加载时，Agent 可能来回切换做法，花掉很多调用次数，却没有完成修复。

另一个可能的情况是，技能中的示例让 Agent 习惯使用某个库，即使当前项目明确要求使用另一个库，它仍沿用示例。此时，安装技能并不一定带来收益。

这些是需要实验复现的示例，不能预先认定所有技能都会产生冲突。已有研究已经评估了技能的实际效用，并观察到部分技能会造成表现下降。[SWE-Skills-Bench](https://arxiv.org/abs/2603.15401)

SkillScope 希望帮助开发者回答三个具体问题：哪些技能一起使用容易出问题？问题在什么条件下出现？能否保留技能的作用，同时减少干扰？

## 用户会怎样使用

用户提供一个代码仓库、一组任务和若干技能文件。SkillScope 在相同环境下运行不同技能配置，通过独立测试判断任务是否完成，再生成诊断报告。

例如，报告可以指出：技能 A 和技能 B 单独运行正常，组合加载时在某类任务上稳定退化；把 A 限制在调查阶段、B 限制在修改阶段后，完成率有所恢复。这里的结果需要真实实验支持，不能根据文本看起来矛盾就直接下结论。

运行流程如下：

1. 读取任务、技能文本和执行环境配置。
2. 比较不加载、单独加载、组合加载等配置，并重复运行。
3. 对表现退化的组合逐步移除技能或指令片段，寻找仍能复现问题的小规模组合。
4. 检查加载顺序、上下文长度和技能内容分别带来了什么影响。
5. 生成按任务阶段加载的策略，在新任务上验证效果。

## 创新点准备放在哪里

### 在随机结果中定位稳定的冲突组合

大模型同一任务运行多次，结果也可能不同。因此，单次失败不足以说明某个技能有害。

拟研究的方法是把逐步缩小组合的搜索与重复实验结合：优先测试有信息价值的组合，在预算内寻找较小且稳定造成退化的集合，并保留证据不足的结论。这里追求的是可复现的小规模冲突集合，不保证找到全局最小集合。

### 区分技能冲突与上下文变长

同时加载更多技能，既改变了指令内容，也增加了输入长度。表现变差可能来自其中任意一个因素。

拟加入长度相近的对照文本、不同加载顺序和单技能实验，减少错误归因。对照文本本身也可能影响模型，需要重复和更换对照进行检查。这些实验提供诊断证据，而不是对模型内部原因的完全证明。

### 把诊断结果转化为有作用范围的加载策略

项目希望进一步生成明确的使用规则，例如调查阶段加载根因分析技能，修改阶段加载实现技能，验收阶段加载测试技能。

第一版由外部状态机决定阶段。切换阶段时重新构建模型输入，只保留必要的任务记录，避免把旧技能原文一直留在历史里。模型已经产生的推断仍可能受旧技能影响，因此需要通过实验衡量隔离效果。

项目的拟研究贡献是“组合诊断与作用域控制的结合”。技能干扰现象、逐步缩小失败样例的方法和按需加载技能都不是独立的新发明，正式开发前还需进一步比较同类工作。

## 建议技术栈

| 技术 | 通俗解释 | 在项目中的用途 |
| --- | --- | --- |
| Python | 编写核心逻辑的语言 | 实现实验执行、组合搜索和加载策略 |
| LangGraph | 把 Agent 的工作划分成明确步骤 | 固定调查、修改、验证阶段，提供技能加载的接入位置 |
| Pydantic | 检查数据是否符合约定格式 | 定义任务、技能、运行记录和诊断结果 |
| asyncio | 管理多个等待中的调用 | 在预算和并发限制内安排实验 |
| 模型供应商 SDK | 与模型接口通信 | 第一版只接入一个支持工具调用的模型 |
| pytest | 自动检查代码是否正确 | 为任务提供独立评分，并验证加载策略的行为 |
| Docker | 为每次实验提供可重置的环境 | 保持代码和依赖一致；Windows 下可通过 WSL2 使用 |
| SQLite 与 JSONL | 保存结构化结果和逐步日志 | 记录技能组合、执行轨迹、费用与评分 |
| NumPy 与 SciPy | 处理数据和不确定性 | 比较重复实验的表现，估计差异范围 |
| Typer | 制作命令行入口 | 提交任务、启动诊断和导出报告 |

第一版生成 Markdown 或 HTML 报告即可。需要交互界面时，再增加 FastAPI 和 Vue 3，不把前端作为核心贡献。

## 第一版做到什么程度

先固定一个 Agent 运行配置，选择 6 至 10 个技能和一组可由测试评分的代码任务。先用小规模重复实验找出几个稳定的组合退化案例，再实现组合缩减和阶段加载。

第一版交付四项内容：可重现的案例、能定位较小冲突组合的诊断程序、阶段加载策略，以及包含原始结果的对照报告。任务、测试和评分程序需要与 Agent 可修改的代码分开管理，防止它修改规则来获得通过。

## 怎样证明方法有用

对照方案包括全部加载、按任务相关性选择技能、人工安排阶段，以及 SkillScope 自动生成的策略。不同方案使用相同模型版本、任务环境和运行预算，并记录实际调用成本。

主要看任务完成率、诊断花费的调用次数、错误停用有益技能的比例，以及新任务上的效果。新增成本也要计入，不能只报告成功案例。

用于寻找冲突的任务与最终测试任务分开。第一版只能说明方法在所测任务和模型上是否有效，不能据此声称对所有技能都适用。

## 开发后适合展示什么

最有说服力的演示是一条完整证据链：某组技能导致稳定退化，诊断器找到相关组合，加载策略缓解问题，并在新任务上保留收益。

简历中可以围绕组合诊断、随机实验设计、Agent 运行控制和可复现评测描述贡献，实际效果填写真实测量结果。
